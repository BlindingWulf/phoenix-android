# Mythos backend and security brief

## Goal
Find and **fix** real weaknesses in Phoenix's hosting backend, while keeping every working hosting feature, normal Java/Bedrock connectivity and low latency.
- This is not a call for a rewrite or a maximal lockdown.
- Fix practical vulnerabilities with minimal, tested changes.

## Ground rules
1. **Every change** comes with:
   - a threat scenario;
   - source evidence or a reproducible test;
   - severity;
   - a minimal fix;
   - regression tests;
   - a performance-impact note;
   - a rollback path (normally: revert the one commit).
2. **Keep hosting working.**
   - Do not remove a feature because it is hard to secure.
   - Do not restrict the game ports (Java TCP, Bedrock/Geyser UDP, Simple Voice Chat UDP), and do not break playit.gg, NetBird or Minecraft.how.
3. **Hot path:**
   - Never add per-packet work to the gameplay path.
   - Put defences at connection boundaries (accept, handshake, login), in app-owned listeners, or in parsers of untrusted input.
4. **Network changes:**
   - Compare against the unchanged baseline: functional (Java join, Bedrock join where possible, status ping) and latency (loopback connect and ping time, before and after).
   - Use loopback fixtures only.
5. **Never** run DoS/load traffic against public servers, Minecraft.how, NetBird, playit.gg or any third party. Volumetric DDoS needs upstream mitigation: do not claim an app patch solves it.
6. **Never** add destructive "repair" operations on user worlds. Integrity fixes must fail closed and keep the user's data.
7. **Defaults:**
   - Keep Java AOT ("Faster starts") **off by default**. It crashes HotSpot C1 when enabled; that root cause is not fixed.
   - Keep Phoenium *Accelerated* opt-in.
   - Never enable device-specific (H-BIG) scheduling by default.
8. **Process:**
   - One topic per pull request, against `main`, with tests.
   - Nothing merges into the validated beta without maintainer review and a real-phone re-check.

## Architecture in one paragraph
- The UI (`MainActivity`, Compose screens) talks to `PhoenixViewModel` → `PhoenixBackend` (`app/.../PhoenixBackend.kt`, the main orchestrator, ~3,400 lines).
- `PhoenixBackend` provisions the server (`core/.../provision`), writes `server.properties` and mod configs, and starts the Java 25 runtime as a **child process** through the installed native launcher `libphoenixjvm.so` (`runtime/phoenix_jvm.c`) using `ProcessBuilder` with an argument list (no shell).
- `core/.../ServerController` and `ProcessRuntimeHost` serialise lifecycle operations and pump stdout/stderr lines back into `PhoenixBackend.consume()`. **That stream is where player-controlled text enters the app** (chat is logged by the server).
- `HostingService` is the foreground service.
- Remote access:
  - `PlayitAgent`/`PlayitManager` run the official playit agent;
  - `NetBirdVpnService` embeds the NetBird Go client (`VpnService` TUN);
  - `NameFrontDoor` is an app-owned TCP listener that routes custom-name logins;
  - `ProxyPairingHost` pairs an optional self-hosted Oracle relay (`deploy/oracle-proxy`).
- `MinecraftHow*` handles the optional hostname provider (HTTP client, DNS checks, Custom Tab sign-in).
- Worlds, mods and backups: `WorldManager`, `ModManager`/`ModChecks`/`ModPacks`, `core/.../world`.

### Design notes (document; do not "fix" by removing features)
- **NET-5, F9: public routes hide player IPs.** Behind playit/NetBird, Minecraft sees the tunnel address, so IP bans and per-IP limits do not work. Any rate limit must key on something that is real at that boundary.
- **NET-6: `accepts-transfers=true` and `enforce-secure-profile=false`** are acceptable only while `online-mode=true`. Keep that invariant and test it.
- **NET-10: the embedded NetBird client** accepts management-pushed routes and DNS, and peers can reach every `0.0.0.0` listener. Document a recommended NetBird access policy rather than binding the game to loopback.
- **A10: the debug-only JVM experiment file** accepts arbitrary flags. It must stay debug-only; confirm release builds never read it.

## What you can test on a desktop vs on a phone
- **Desktop:**
  - parsers and state machines (JVM unit tests);
  - loopback listeners (`NameFrontDoor`, `ProxyPairingHost`, the status probes) with fake clients;
  - archive handling with crafted ZIPs;
  - provisioning with fake transports;
  - a real 26.2 dedicated server on `127.0.0.1` for console/log formats.
- **Phone only:** see [`MYTHOS_START_HERE.md`](MYTHOS_START_HERE.md#phone-only-checks). Mark such pull requests `needs-device-check`.
